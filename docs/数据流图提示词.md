# 数据流图（DFD）绘制提示词

> 用途：让 AI 按软件工程规范产出「论文阅读助手」的分层数据流图，帮助全组统一对系统的理解。
> 用法：把下面【提示词正文】整段复制给 AI；拿到输出后，把图贴进 Mermaid Live（https://mermaid.live）或直接提交到仓库由 GitHub 渲染。
> 成品图见 [`dfd/`](dfd/)（0 层 / 1 层 / 两张 2 层分解，含评审发现）。

---

## 提示词正文（复制从这里到「提示词结束」）

```text
你是软件工程需求分析专家，熟悉 Yourdon/DeMarco 结构化分析方法。请为下面这个项目绘制分层数据流图（DFD）。

【项目背景】
项目名：论文阅读助手（PaperMind）
定位：面向本科生、研究生低年级与科研入门者的 Web 端学术论文阅读辅助工具
技术栈：Vue 3 + PDF.js（前端）｜Spring Boot（业务后端）｜FastAPI + PyMuPDF（PDF 解析与 RAG 服务）｜PostgreSQL + pgvector（向量库）｜Redis（缓存）｜本地文件存储

【本期（Alpha 迭代）已确定的功能范围】
F1 文献上传与列表：用户上传 PDF，系统存盘并记录元数据（标题/页数/上传时间），列表可查
F2 PDF 在线阅读：浏览器内渲染 PDF，支持翻页、缩放、跳指定页
F3 单篇精读问答：针对某一篇论文提问，系统检索该论文相关段落，返回答案 + 引用原文片段 + 页码；点击页码跳转到对应页
F4 基础工程化：一条命令启动全栈，异常有友好提示，有运行日志

【后续迭代才做，本期不画进主图（可在图后单列「规划中」）】
关键词检索外部学术库并导入（Beta）｜双栏阅读流解析（Beta）｜引用区域高亮框 bbox（Beta）｜登录与多用户（Beta）｜批注与书签（RC）｜跨文献对比（RC）｜阅读行为分析看板（RC）

【外部实体（候选，请你确认或修正）】
读者（本系统唯一用户角色）、本地文件系统（存 PDF 原文件）、大模型服务（外部 API，如 DeepSeek）、学术数据库 API（本期不接入）

【绘制要求】
1. 分层绘制，至少三层：
   - 0 层（上下文图）：整个系统作为一个加工，画出与所有外部实体的数据流
   - 1 层：把系统分解为 4～6 个主要加工，画出加工之间、加工与数据存储之间的数据流
   - 2 层：只对最关键的 2 个加工再分解（建议「解析论文」与「回答问题」）
2. 严格遵守 DFD 四要素，不要混入控制流、时序、判断分支（那是时序图/流程图，不是 DFD）：
   - 外部实体：矩形，编号 E1、E2…
   - 加工（处理）：圆角矩形或圆形，编号 P1、P2…，名称必须是「动词 + 名词」短语，如「解析论文」「检索相关段落」
   - 数据存储：开口矩形或圆柱，编号 D1、D2…，名称是名词，如「论文库」「段落向量库」
   - 数据流：带箭头连线，线上必须标注数据流名称（名词短语），如「PDF 文件」「问题文本」「答案与引用」
3. 平衡原则：父图中某个加工的输入输出，必须与它分解后的子图的输入输出完全一致；不允许凭空出现或消失数据流
4. 每个加工至少有一个输入流和一个输出流；不允许只有输入没有输出的「黑洞」，或只有输出没有输入的「奇迹」
5. 图中不出现技术产品名（不要写 Redis、PostgreSQL、Spring Boot）。技术实现只在图后的「实现对照表」里说明
6. 数据存储必须既有写入流也有读取流（除非明确标注为只写/只读）

【输出格式】
按以下顺序输出，全部用中文：

一、要素清单
用三张表列出：外部实体（编号/名称/说明）、加工（编号/名称/一句话职责/所属层次）、数据存储（编号/名称/存什么/主要读写者）

二、0 层图
用一个 ```mermaid 代码块输出（flowchart LR）。节点形状：外部实体用 [ ]，加工用 ( )，数据存储用 [( )]

三、1 层图
同样用 mermaid 代码块输出

四、2 层图（两张）
分别针对「解析论文」与「回答问题」两个加工输出 mermaid 图

五、数据流明细表
逐条列出：编号 F1、F2…｜起点｜终点｜数据流名称｜承载内容说明

六、平衡性自检
逐项说明：每张父子图的输入输出是否一致；有没有黑洞/奇迹加工；有没有只写不读的存储。发现问题就当场修正并说明改了什么

七、实现对照表
把 DFD 里的抽象要素映射到本项目的具体实现，例如「D2 段落向量库 → pgvector 的 chunks 表」「P4 检索相关段落 → 向量相似度检索」

八、待确认项
列出你无法从上述信息中确定、需要我补充的内容（不要自己编造需求）

【重要约束】
- 不要编造项目中未提到的功能或外部系统
- 名称必须具体，禁止出现「处理数据」「信息」这类空泛命名
- 如果某个信息缺失，写进「待确认项」，不要用臆测填补
```

## 附一：DFD 符号速查（画完自查用）

| 要素 | 图形 | 命名规则 | 本项目示例 |
|---|---|---|---|
| 外部实体 | 矩形 | 名词 | E1 读者、E2 大模型服务 |
| 加工 | 圆角矩形 / 圆 | **动词 + 名词** | P2 解析论文、P5 生成答案 |
| 数据存储 | 开口矩形 / 圆柱 | 名词 | D1 论文库、D3 段落向量库 |
| 数据流 | 带箭头连线 + 标注 | 名词短语 | 「PDF 文件」「问题文本」「答案与引用」 |

## 附二：最常见的五个错误（review 时直接对照）

| ❌ 错误 | 为什么错 | ✅ 正确做法 |
|---|---|---|
| 图上画了 if/else 判断 | DFD 不表达控制逻辑 | 判断放到状态图或判定表 |
| 加工名写「数据处理」 | 无法判断职责 | 写「解析论文」「检索相关段落」 |
| 箭头没标数据流名称 | 不知道传了什么 | 每条流都必须命名 |
| 父图有「引用坐标」子图没有 | 违反平衡原则 | 父子图输入输出必须一致 |
| 图里写 Redis / pgvector | 混入实现细节 | 图里写「缓存」「向量库」，实现放对照表 |

## 附三：拿到 AI 输出后必须人工核对的三点

1. **平衡性**：0 层里系统对外只有「PDF 文件进、答案出」，1 层、2 层不能多出别的对外流
2. **是否漏了 F3 的页码**：页码与引用片段是 Alpha 的核心数据流，图里必须有
3. **是否越界**：图里不该出现「检索外部学术库」「阅读看板」——那是 Beta/RC 范围
