## 二、核心结论：**超时是兜底，不是常态**

> **正常情况下几乎不会触发超时。** 超时的作用只有一个：**外部依赖卡死时，给用户一个明确出口，而不是无限转圈或 500。**

### 1. 预算 vs 正常耗时

| 超时 | 正常耗时 | 配置预算 | 余量 |
|---|---|---|---|
| 检索 | 1–3 秒 | **30 秒** | ≈ **10 倍** |
| 问答 / 划词 | 2–8 秒 | **25 秒** | ≈ **3–10 倍** |
| 解析 | 10–60 秒 | **180 秒** | ≈ **3–10 倍** |
| 导入 | 3–20 秒 | **60 秒** | ≈ **3–10 倍** |

**结论**：预算普遍是正常耗时的 3–10 倍，正常使用不会碰到。

### 2. 正常使用中“可能”逼近超时的原因（都是异常态）

| 原因 | 影响哪条超时 | 说明 |
|---|---|---|
| **网络波动 / 校园网拥塞** | 检索、导入、问答、划词 | 最常见；表现为变慢或直接不可达 |
| **arXiv / OpenAlex 变慢或被限流** | 检索、导入 | 限流（429）通常是**快速失败**，不是超时 |
| **LLM 高峰期排队** | 问答、划词 | DeepSeek 侧延迟升高，可能接近 25s |
| **ai-service 冷启动** | 解析、问答 | 首次加载 bge-m3 模型需 30–60s |
| **论文过大 / 版面复杂** | 解析 | 页数多、公式表格多，解析时间显著变长 |
| **多人同时使用（并发）** | **解析 / 导入（主）、问答检索（次）** | 单机单 worker，解析与 embedding 是 CPU 密集，并发会互相拖慢；问答/划词主要是等外部 LLM，受影响较小 |

> 注意：**“不可达/限流”多数是几秒内快速失败**，走的是降级或错误码，不是等满超时。

### 3. 判断超时设计是否合理的标准

1. **预算 > 正常耗时 p95**（否则就是 BUG-010 那种“必然超时”）；
2. **超时后必须有出口**：`degraded` / `3002` / `parseStatus=failed`，不能白屏或 500；
3. **不靠“等自然发生”验证**，而是**故障注入**（只接不回、黑洞地址、暂停 ai-service、断网、注入小超时）。

## 三、今日实测明细

### 1. 检索超时（B18-01）✅

| 项 | 内容 |
|---|---|
| 构造 | 将 `APP_SEARCH_ARXIV_URL` 指向“只接不回”的 TCP 服务（`host.docker.internal:9999`） |
| 实测 | **30.11 秒** |
| 返回 | HTTP 200，`{"code":0,"message":"外部数据源不可用，请稍后重试","data":{"total":0,"cached":false,"degraded":true,"items":[]}}` |
| 对照 | 指向不可达地址 `10.255.255.1` → **5.18 秒**快速降级（连接失败，非读超时） |
| 判定 | **通过**（≤31s、degraded、提示正确） |

### 2. 断网降级（B18-02，相关）✅

| 场景 | 实测 |
|---|---|
| 有缓存（同参数） | `cached=true`、`total=104302`、message「离线缓存（更新时间 2026-11-26 19:01:41）」 |
| 无缓存（新关键词） | `items=[]`、`degraded=true`、message「外部数据源不可用，请稍后重试」 |
| 恢复网络 | `degraded=false`，新关键词可正常搜到 |

### 3. 问答超时 ✅

| 项 | 内容 |
|---|---|
| 构造 | `docker pause papermind-ai`（连接可建立、永不响应） |
| 实测 | **25.06 秒** |
| 返回 | `{"code":3002,"message":"AI 服务超时","data":null}`（HTTP 504） |
| 判定 | **通过** |

### 4. 划词超时（后端 25s + 前端 15s）✅

| 层 | 实测 | 返回/表现 |
|---|---|---|
| 后端 `/api/explain` | **25.04 秒** | `3002 AI 服务超时` |
| 前端 `/reader/53` 划词 | 约 **15 秒** | 弹窗「解释服务响应超时（>15s），请稍后重试」+ 重试按钮 |

**观察项**：前端预算 **15s < 后端 25s**，前端先取消、后端白跑约 10 秒（S2，建议前端调到 28–30s）。

### 5. 解析超时（机制验证）✅

| 项 | 内容 |
|---|---|
| 构造 | 临时后端 `-e APP_PARSE_TIMEOUTSECONDS=5 -e AI_SERVICE_URL=http://host.docker.internal:9999` |
| 实测 | 上传后约 15 秒内状态落定 |
| 返回 | `parseStatus=failed`，`parseError`：「**解析超时：AI 服务未在 5 秒内返回（文档切片较多或服务繁忙）**」 |
| 判定 | **通过**（用 5s 代替默认 180s，机制一致） |

### 6. 导入超时（机制验证）✅（有观察项）

| 项 | 内容 |
|---|---|
| 构造 | 临时后端 `-e APP_IMPORT_TIMEOUT=1`，导入一篇**未入库**的 arXiv 论文（2401.05779） |
| 实测 | **1.035 秒** |
| 返回 | `{"code":3001,"message":"全文下载失败或不是 PDF：https://arxiv.org/pdf/2401.05779"}` |
| 数据 | 未创建 `papers` 记录（导入后用户论文数不变） |
| 判定 | **机制通过**；文案不区分“超时/404/非 PDF”，记 **S2 可诊断性观察** |

### 7. 前端问答超时 ✅

| 项 | 内容 |
|---|---|
| 构造 | `docker pause papermind-ai`（后端必等 25s） |
| 前端实测 | 约 **25 秒**，页面显示「**请求失败 / AI 服务响应超时（>25s）**，请稍后重试」+ 重试按钮 |
| 后端对照 | curl `/api/qa/ask` **25.05 秒** → `{"code":3002,"message":"AI 服务超时"}` |
| 判定 | **通过**（前端 25s 取消生效） |

**观察**：前端 25s 与后端 25s **完全相等**，弱网时前端会先取消、后端白跑；且与契约 `qa_ask_seconds: 30` 不一致，建议前端调到 28–30s。

## 五、结论（答辩口径）

> “**超时是兜底，不是常态。** 我们所有超时预算都是正常耗时的 3–10 倍，正常使用几乎碰不到。
> 全链路共 7 处超时，今天实测 6 处：检索 30.11 秒降级、问答 25.06 秒返回 3002、划词后端 25.04 秒 / 前端 15 秒先取消、前端问答 25 秒提示、解析注入 5 秒后 failed、导入注入 1 秒后 3001 且不建记录。
> 结论：**外部依赖卡死时都有明确出口，没有白屏或 500**；qa 预算与 3002 文案已由契约 1.3.3 对齐；**explain 后端 12s（1.3.4）仍需代码落地，BUG-031 保持待修复**。
